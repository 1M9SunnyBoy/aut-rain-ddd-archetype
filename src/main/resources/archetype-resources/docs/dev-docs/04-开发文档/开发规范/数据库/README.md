${hash} 数据库开发规范

版本：v1.0；更新：2026-11-02。适用于生成项目的业务数据库。

只定义通用设计、查询、迁移和一致性要求。业务实体、状态、日期范围、人员与权限字段由项目设计决定；不要求所有页面、接口或菜单由数据库配置。若采用配置驱动架构，需另行规定配置完整性和代码能力边界。

${hash}${hash} 1. 基线与初始化职责

当前环境使用 MySQL 8.0.32，业务表使用 InnoDB、utf8mb4，表和字段采用 snake_case。数据库名默认由 artifactId 将连字符转为下划线生成，也可通过 databaseName 指定。

| 位置 | 职责 |
| --- | --- |
| docs/dev-ops/environment/mysql/sql/00-project.sql | 创建项目数据库，不创建业务表 |
| mysql/sql 中的中间件 SQL | 对应中间件的首次初始化，不由业务 Flyway 管理 |
| app-backend 下 app 模块的 src/main/resources/db/migration | 业务结构与受版本管理的必需数据迁移 |
| 独立开发夹具 | 可选演示和测试数据，不自动导入生产 |

MySQL 容器初始化 SQL 只在空数据目录首次执行；修改它不会升级已有数据卷。当前 V1 是 SELECT 1 基线标记，不包含业务表；真正的业务结构由后续迁移创建。

${hash}${hash} 2. 表、字段与约束

每张业务表必须有稳定主键。ID 生成策略由项目统一，BIGINT 对外作为字符串传输。业务编码按需要建立唯一约束，不能仅靠先查询后插入防重。

字段类型、长度、空值、默认值及说明明确：金额等精确值使用 DECIMAL，不使用 FLOAT/DOUBLE；枚举值由领域规则限制，必要时以 CHECK 补充。字典显示标签和领域允许状态应分别定义，新增状态需同步相关契约、约束与测试。

选择适合业务比较语义的字符集排序规则；对大小写敏感的编码明确规则，不默认假定所有字符串比较区分大小写。使用 JSON 字段需明确结构、查询和演进方式，不用它逃避核心关系建模。

审计字段、逻辑删除、租户字段按实际需求设计；不强制所有表都具有这些字段，也不禁止项目使用创建人、修改人等字段。

${hash}${hash} 3. 禁止物理外键与后端兜底

禁止 FOREIGN KEY、外键 REFERENCES 以及外键级联动作。关联字段建立必要索引，保持主键、唯一约束、CHECK 等有效约束；物理外键禁用不代表取消数据完整性要求。

后端在同一事务中校验父记录存在、有效状态与数据归属，并结合锁或版本协议处理并发。父对象删除、移动或状态变更同样遵循协议；仅在子对象写入时检查一次存在性无法防止并发孤儿。

每个业务定义固定锁顺序，同类记录按稳定 ID 排序。删除策略明确为拒绝、有序清理、归档或其他已确认方式，不提供隐式级联。批处理、导入和运维写入同样遵守关联规则。

发布前静态检查 SQL 的外键定义，并在目标业务库核实物理外键数量为 0。检查应识别 SQL 结构，不能看到 ON UPDATE 就报错：ON UPDATE CURRENT_TIMESTAMP 是字段更新时间机制，不是外键级联。注释中的禁用规则也不应被识别为实际建表约束。

完整性诊断用于发现孤儿、无效引用和重复业务数据；默认只读，不静默删除或修复。发现问题后确认来源，再制定修复迁移与验证。

${hash}${hash} 4. 索引与查询

- 索引按实际过滤、连接、排序与唯一性需求设计，避免无依据地给每个字段建索引。
- 约定主键、uk_<含义> 唯一索引及 idx_<含义> 普通索引，名称保持可读并符合长度限制。
- 复合索引结合查询顺序与选择性评估；变更前检查执行计划、扫描量和写入成本。
- 禁止 SELECT *、别名.*，允许 COUNT(*)；字段投影与 DTO/PO 映射一并维护。
- 查询分页有上限，排序包含稳定的唯一字段作为并列排序补充；深分页按需求使用游标，不默认加载全量数据。
- 避免 N+1、无索引的批量更新和无限增长的 IN 列表。慢查询阈值与告警按部署容量制定。
- UPDATE/DELETE 明确作用范围，重要命令检查影响行数。大批量修复先预览数量并分批执行。

${hash}${hash} 5. 日期时间

时间点采用 UTC 存储，业务自然日期使用 DATE。Java 时间点优先使用 Instant 或明确转换规则的时间类型，日期用 LocalDate；接口区分含时区时间点与 YYYY-MM-DD。

DATETIME 不携带时区，CURRENT_TIMESTAMP 受数据库会话时区影响；注释写 UTC、设置容器 TZ 或仅设置 JDBC 参数都不能代替端到端验证。项目需明确应用转换、JDBC、连接会话 time_zone 和数据库默认值的责任，并测试跨时区往返及日期边界。

created_at 不随普通更新改变，updated_at 由应用或数据库明确负责，避免两边规则相互覆盖。历史时间缺失不能为了通过校验而伪造。

${hash}${hash} 6. Flyway 迁移

本脚手架采用递增整数版本：V1__base_schema.sql、V2__description.sql、V3__description.sql 等。并行开发在合并前协调版本，避免重复编号。不要将其他项目的时间戳命名规则强加给已建立整数序列的项目。

已部署的版本化迁移不得修改、删除或改名，修复追加新版本；描述写清变更意图，不把整库导出作为日常迭代迁移。禁止应用启动时自动 clean、baseline 或 repair 来掩盖校验失败。

每个迁移评审：前置版本、影响表与行数、锁与耗时、默认值和回填、代码兼容、验证查询及失败恢复。MySQL DDL 可能隐式提交，不能假设混合 DDL/DML 文件失败就会整体回滚。失败后先检查实际结构与 Flyway 历史，再决定修复步骤，不直接删除历史记录。

滚动升级优先先扩展后收缩：新增兼容结构、上线兼容代码、回填并验证，再在后续版本删除旧字段。数据迁移分批且可核对；恢复旧应用前确认新数据库结构兼容，回滚镜像不等于回滚数据库。

验证至少包含全新空库迁移、上一发布版本带数据升级、唯一/空值/引用检查和应用兼容。需要真实 MySQL 的验证必须在明确授权的隔离环境执行，不能把静态 SQL 检查当作真实升级验证。

${hash}${hash} 7. 数据归属与种子演进

区分必需系统数据、用户维护数据和可选演示数据。系统数据使用稳定编码和有范围的增量 INSERT/UPDATE，明确哪些字段归系统维护；不能用无差别 upsert 覆盖用户修改。

角色、授权关系、账号配置等若由用户维护，升级默认保留；新增系统资源不等于应自动给所有角色授权。涉及权限变更需明确业务决策，不由整库导入或全表删除重建隐式完成。

Flyway 只对尚未执行的版本运行一次，但同版本在各环境都可能遇到不同存量数据。新增唯一数据前检查是否已存在、是否与预期一致，明确冲突策略；不要用 INSERT IGNORE 把结构或数据错误全部吞掉。

演示数据只在独立开发/测试流程导入，检查目标环境及预期空表条件，不随生产迁移自动执行。数据库为空时返回真实空状态，不能由业务接口暗中创建模拟记录。

${hash}${hash} 8. 运维、评审与交付

结构和数据变更前按风险备份，并验证恢复流程；备份包含敏感信息，限制访问与保留周期。对象存储、缓存、消息数据有各自的备份和恢复策略，不由 Flyway 自动覆盖。

审查账号权限、SQL 注入、敏感数据查询与日志输出；开发默认凭据不直接用于生产。禁止以删除数据卷解决正常迭代问题。更新迁移时同步设计文档、查询、映射和必要测试。

| 检查方式 | 检查内容 |
| --- | --- |
| 静态/人工评审 | 迁移编号、历史文件变更、显式字段、外键定义、索引与回填范围 |
| 隔离库集成验证 | 真实迁移、唯一约束、逻辑引用、并发冲突、查询计划 |
| 发布验证 | 备份可恢复、Flyway 历史、应用兼容、关键数据数量 |

这些是交付要求，不表示模板已自动实现全部数据库审计工具。完整性检查不得代替后端事务，静态检查不得代替有数据升级验证。
