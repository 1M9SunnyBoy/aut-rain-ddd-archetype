${hash}${hash} 1. 目标与术语

本规范将稳定发布、集成开发、历史快照、发版候选和个人开发工作隔离，确保开发人员只在本人工作分支提交，管理人员统一完成校验、合并、发版与归档。

本规范统一使用 `develop` 作为集成开发分支名称。管理人员指承担审查、集成和发布职责的维护者，不要求特定组织职级。仓库采用本规范前应完成第 10 节的落地配置；现有分支名称不同的项目按第 11 节迁移。本文不自动创建分支、修改仓库权限或执行清理任务。

1. **分支是可移动的协作引用**，不能单独作为不可篡改的版本凭据。
2. **发布 Tag 按制度禁止修改**。Git 本身允许移动或删除 Tag，必须通过托管平台保护、权限和审计落实。每个正式版本同时保留受保护的 `version{num}` 分支与带注释的 `v{num}` Tag，发布记录固定对应的完整提交 SHA；按团队要求可使用签名 Tag。
3. 所有时间均使用中国标准时间（UTC+08:00），格式为 `YYYYMMDDHHmm`，精确到分钟，例如 `202608171430`。
4. 分支名只使用小写 ASCII 字母、数字和短横线；不使用空格、中文、斜杠或额外下划线。下划线只用于分隔工作类型与工作内容。

${hash}${hash} 2. 分支类型与权限

| 分支类型 | 命名 | 内容与生命周期 | 允许操作人 |
| --- | --- | --- | --- |
| 稳定主分支 | `main` | 最近一次已验收、可部署和可回滚的正式版本代码。只由管理人员从完成发布验证的 `develop` 合入。 | 管理人员合并；仓库管理员保护 |
| 集成开发分支 | `develop` | 当前迭代已经通过审查与基础校验的最新开发代码。所有成员工作分支均从此分支创建；只有管理人员可以将审查合并分支合入此分支。 | 管理人员合并；仓库管理员保护 |
| 上版本快照 | `history` | 上一个正式版本的 `main` 快照。每次发布前由管理人员移动到当前 `main` 指针，发布后只读。 | 管理人员维护；仓库管理员保护 |
| 审查合并分支 | `{YYYYMMDDHHmm}-review` | 由管理人员从 `develop` 创建，用于审查和集成一批成员工作分支。例如 `202608171430-review`。审查结束后必须在创建后 48 小时内删除。 | 管理人员维护；仓库管理员保护 |
| 成员工作分支 | `{YYYYMMDDHHmm}-{成员标识}-{类型}_{内容}` | 单一工作项的开发、修复、文档或测试改动。云端分支最长保留 48 小时，完成合并或关闭后立即删除。 | 对应成员创建、提交和推送；管理人员合并、清理 |
| 版本归档分支 | `version{num}` | 从正式 `main` 版本创建的只读归档，例如 `version1.0.0`。必须与同一提交的 `v1.0.0` 注释 Tag 成对存在。 | 管理人员创建、维护；仓库管理员保护 |

`history` 只保留一个“上一版本”快照，不能承担全部历史归档职责。全部正式版本必须通过 `v{num}` Tag 与 `version{num}` 分支保留；不得只依赖 `history` 查找旧版本。

${hash}${hash} 3. 成员工作分支命名

${hash}${hash}${hash} 3.1 格式

```text
{YYYYMMDDHHmm}-{member}-{type}_{work}
```

示例：

```text
202608171430-dev01-feat_auth-login
202608171515-dev02-fix_gateway-route
202608171600-dev03-docs_api-contract
202608171645-dev04-test_api-validation
```

| 字段 | 规则 | 示例 |
| --- | --- | --- |
| `YYYYMMDDHHmm` | 分支首次创建的 UTC+08:00 时间，不因后续提交修改。 | `202608171430` |
| `member` | 提交人与代码托管平台一致的小写成员标识；不得使用真实姓名、手机号或临时昵称。 | `dev01` |
| `type` | 见下表中的受控缩写。 | `feat` |
| `work` | 简短、稳定的小写 kebab-case 工作描述；不含额外下划线。 | `auth-login` |

| 类型 | 含义 | 典型使用场景 |
| --- | --- | --- |
| `feat` | 新功能 | 新增项目查询、申请创建页面 |
| `fix` | 缺陷修复 | 修复鉴权、接口兼容或页面错误 |
| `update` | 已有能力的非破坏性调整 | 调整依赖、配置或展示规则 |
| `refactor` | 不改变外部行为的重构 | 收敛重复请求封装 |
| `docs` | 文档 | 接口、开发或运维文档 |
| `test` | 测试 | 新增或修复单元、集成、端到端测试 |
| `build` | 构建与 CI | Maven、npm、流水线或镜像构建 |
| `chore` | 维护性杂项 | 工具配置、忽略规则、仓库整理 |

建议的校验正则为：

```text
^(?:main|develop|history|version[0-9]+\.[0-9]+\.[0-9]+|[0-9]{12}-review|[0-9]{12}-[a-z0-9-]+-(?:feat|fix|update|refactor|docs|test|build|chore)_[a-z0-9][a-z0-9-]*)${dollar}
```

正则只校验名称形态；日期真实性、成员身份、版本唯一性及分支创建时刻还需由平台或自动化校验。成员标识与工作描述使用 ASCII 小写字母、数字和短横线，不能用重命名刷新 48 小时期限。

${hash}${hash} 4. 开发人员工作流

开发人员只负责自己工作分支的代码质量，不负责 `develop`、`main`、`history`、审查合并分支或版本分支的合并与移动。

1. 从远程最新 `develop` 创建工作分支，禁止从 `main`、`history`、`*-review`、`version{num}` 或他人工作分支创建。
2. 在自己的工作分支完成代码、测试、接口或文档改动；提交信息使用清晰中文或 Conventional Commits 风格，禁止“修改”“测试”等无语义信息。
3. 管理人员创建当前审查合并分支后，向该 `{YYYYMMDDHHmm}-review` 发起 PR/MR，并填写工作项、影响范围、验证命令、接口/迁移影响和回滚说明。
4. 根据评审意见只在本人工作分支继续提交。合并前如 `develop` 已更新，可将本人未共享的工作分支 rebase 到最新 origin/develop，或经团队约定将 origin/develop 合并到本人工作分支。不得将本人改动自行合入受保护分支。已推送的工作分支若需 rebase，应先协调评审和协作者，再使用 --force-with-lease 更新本人分支，禁止使用无条件 --force。
5. 不得直接推送、合并、重写历史、删除或提交代码至 `develop`、`main`、`history`、`{YYYYMMDDHHmm}-review`、`version{num}`。

推荐命令：

```bash
git fetch origin
git switch -c 202608171430-dev01-feat_auth-login origin/develop
git add <文件>
git commit -m "feat(web): add login page shell"
git push -u origin 202608171430-dev01-feat_auth-login
```

${hash}${hash} 5. 管理人员集成与发布工作流

${hash}${hash}${hash} 5.1 审查并集成到 `develop`

1. 管理人员从当前 `develop` 创建一个 `{YYYYMMDDHHmm}-review` 审查合并分支，并告知本批次成员 PR/MR 的目标分支。
2. 校验工作分支命名、来源分支、提交范围、代码审查结论和 CI 结果；确认迁移、接口、错误码、前端权限和部署影响已按项目规范同步。
3. 管理人员将通过校验的成员 PR/MR 合并到当前审查合并分支，保留可追溯的 PR/MR 记录；不得由开发人员自行合并。
4. 在审查合并分支完成批次级构建、测试与人工审查后，管理人员将该分支合并到 `develop`。未通过的成员分支不得进入 `develop`；审查结束后按第 8 节删除临时分支。
5. 合并后再次验证 `develop`，失败时优先回滚该次合并或通过新的工作分支修复，禁止直接在受保护分支临时改代码。

${hash}${hash}${hash} 5.2 发布流程

1. 管理人员宣布迭代冻结，并确认 `develop` 已通过发布前 CI、测试和文档检查。
2. **在合并 `develop` 前**，记录当前 main 的完整提交 SHA，将 history 指向该旧 main 提交，并核验上次发布 Tag。首次发布没有上一正式版本时不创建虚假的 history 快照；main/develop 的首次建立按第 10 节办理。
3. 通过验收后，由管理人员将 `develop` 合并到 `main`，创建带注释的 `v{num}` Tag，并从同一提交创建只读 `version{num}` 分支。
4. 禁止向 main、history、版本分支及发布 Tag 直接提交业务改动；main/history 仅允许受控发布动作更新，版本归档与已发布 Tag 不再移动。记录版本号、完整提交 SHA、制品版本或摘要、验证结果和数据库迁移兼容说明。审查分支不承担版本归档职责。
5. 本流程中的补丁仍经 develop 正常集成后发布；若 develop 含不能上线的变更，不得为修复线上问题把它们一起发布。管理人员须先确定发布范围或制定独立的紧急修复流程，不能未经约定从旧版本直接修改 main。

示意：

```text
成员工作分支 --PR/MR--> 202608171430-review --审查通过--> develop --正式发版--> main
                                ^                                   |                 |
                                |                                   |                 +--> v1.0.0 Tag
                          管理人员从 develop 创建                    |                 +--> version1.0.0
旧 main -----------------------------管理人员更新-------------------> history
```

${hash}${hash} 6. 分支保护与合并门禁

代码托管平台应对 `main`、`develop`、`history`、`*-review` 和 `version*` 设置以下保护：

| 规则 | `main` | `develop` | `history` / `version` | `*-review` |
| --- | --- | --- | --- | --- |
| 直接推送 | 禁止 | 禁止 | 禁止 | 禁止 |
| 开发人员合并 | 禁止 | 禁止 | 禁止 | 禁止 |
| 管理人员 PR/MR 合并 | 允许 | 允许 | history 仅允许受控发布更新；version 只允许首次创建 | 允许 |
| 强制推送 | 禁止 | 禁止 | 禁止 | 禁止 |
| 删除分支 | 禁止 | 禁止 | 禁止 | 允许，但只能在审查结束或超过 48 小时后由管理人员执行 |
| 必须通过 CI | 是 | 是 | 发布、归档操作前必须通过 | 是 |
| 最少审批 | 1 名管理人员 | 1 名管理人员 | 1 名管理人员 | 1 名管理人员 |

CI 必须覆盖以 *-review、develop 和 main 为目标的 PR/MR，以及合并后的必要验证；状态检查名称与分支保护要求一致。不能只监听 main 就宣称所有合并已受 CI 保护。发布 Tag v* 需单独设置禁止更新/删除的保护规则。

受保护分支的首次创建、history 发布更新以及审查分支清理由授权维护者或专用自动化身份完成，只允许对应操作，不开放常规直接推送。history 在正常线性发布历史中应可快进更新；若非快进则停止并调查，不通过临时强推绕过保护。平台不能细分创建/删除权限时，应记录最小范围、限时例外和审计结果。

${hash}${hash} 7. 提交、PR/MR 与审查要求

PR/MR 至少包含：工作项、变更目的、影响范围、验证命令与结果、接口/响应码/数据库迁移影响、配置与部署影响、恢复方案。没有执行的验证明确标注，不能写为通过。

提交不包含密钥、构建产物、依赖缓存或本地日志。合并策略由仓库统一，避免在同一批次随意混用 squash、merge 和 rebase；选择 squash 时保留 PR/MR 与合并提交的关联记录。

新增提交后需要重跑相关检查；审批应针对实际待合并内容，启用平台支持的过期审批失效规则。至少一名非提交人的授权维护者审批；单人仓库无法满足时须明确记录例外，不宣称已完成独立审批。

${hash}${hash} 8. 临时分支生命周期与云端清理

1. 成员工作分支和 `{YYYYMMDDHHmm}-review` 都是临时分支；云端留存时间从分支创建时间起计算，最长不得超过 48 小时（UTC+08:00），不因周末、节假日或等待评审而顺延。
2. 成员工作分支合并或关闭后，成员立即通知管理人员清理远程分支；管理人员负责确认并删除，不能以“代码已合入”为由继续长期保留。
3. 审查合并分支完成合并、审查驳回或批次终止后，管理人员必须立即删除；无论状态如何，创建满 48 小时必须删除。
4. 48 小时内未完成审查的批次不得延长原分支寿命。管理人员关闭旧 `review` 分支并从最新 `develop` 创建新的 `review` 分支，未合入的成员工作内容需通过新的工作分支重新提交或按 PR/MR 记录恢复。
5. 远程分支删除通常保留 PR/MR 和评审记录，但不保证未合并的提交对象或 CI 制品被永久保存。删除前必须核实已合并，或把未合并工作及其 SHA 保存到批准的补丁/归档介质，记录恢复方法；不得只依赖平台可能保留的悬空提交。
6. 管理人员至少每日检查远程临时分支，使用到期提醒或自动任务确保不超过 48 小时；仅每日检查无法保证严格截止时间。Git 引用本身没有可靠的创建时间，需在首次创建时记录平台事件或可信登记时间，与分支名时间核对，不得用最后提交时间代替。未合并工作的保存应在到期前完成；清理失败或无法安全保存时告警并记录例外，不得静默丢弃工作。
7. 本地工作分支可由成员自行保留，但不得通过本地分支绕过远程分支保护；成员离开项目或工作项关闭后应主动删除本地副本。

${hash}${hash} 9. 版本与历史保留

1. 推荐采用语义化版本号 `MAJOR.MINOR.PATCH`，例如 `1.0.0`、`1.1.0`、`1.1.1`。Tag 固定为 `v1.0.0`，分支固定为 `version1.0.0`。
2. `version{num}` 分支与 `v{num}` Tag 必须指向同一提交。受保护的 Tag 与发布记录中的完整提交 SHA、制品摘要共同用于审计、部署和恢复；分支用于浏览和兼容既定分支结构。代码版本恢复不保证数据库和外部数据可以回退，发布前需确认兼容性。
3. `history` 指向发版前的旧 `main`，因此它只代表一个上一版本。需要回溯任意旧版本时使用对应 Tag，不得移动 `history` 寻找历史。
4. 不得对已发布 Tag、`version{num}` 或 `history` 做 rebase、force push 或新增业务提交；history 仅在下一次正式发布时按第 5 节受控更新；临时 `review` 分支按第 8 节到期删除，不做版本归档。

${hash}${hash} 10. 项目采用前的配置清单

1. 指定唯一协作主远程。本文用 origin 作为示例名称，多远程镜像项目需指定同步方向、责任人及故障处理，避免多个远程独立接受合并。
2. 明确默认分支、版本策略、首次正式版本号、维护者名单、审批及合并策略。版本号采用 MAJOR.MINOR.PATCH，预发布命名如有需要另行扩展保护和校验规则。
3. 空仓库由授权维护者导入经过审查的初始提交并建立 main/develop，随后启用保护；首次正式发布创建成对 Tag 和版本分支。初始工程不自动等于已验收的正式版本。
4. 在托管平台实际配置分支/Tag 保护、审批、CI、发布权限和临时分支到期清理。首次合并验证 CI 真正触发、失败能够阻止合并。
5. 建立分支创建时间登记和未合并工作恢复机制。48 小时是本规范的协作政策，不是 Git 的技术限制；大型工作需拆成可审查的小批次。团队采用不同期限时必须修订本文及自动化规则，不能只在口头上延长。
6. 首次发布前演练版本定位和恢复，核验 Tag 与 version 分支的提交一致。本文和模板生成过程不自动操作远程仓库。

${hash}${hash} 11. 现有开发分支名称迁移

本节仅适用于现有集成分支尚未命名为 develop 的项目，新仓库无需执行迁移。

1. 管理人员通知成员暂停向旧集成分支推送，清点未合并 PR/MR、CI、部署及其他自动化引用，记录当前提交 SHA。
2. 在协作主远程创建 develop，使其指向迁移确认的旧分支提交；更新默认开发分支、PR/MR 目标和分支保护规则。
3. 更新 CI 触发、部署脚本、校验规则和文档，实际验证 develop 及审查分支的检查与保护。
4. 通知成员执行 git fetch --prune；未完成工作经协调同步到 origin/develop，不强行重写他人工作分支。
5. 在迁移验收和约定观察期后删除旧分支。删除前确认引用已切换、未合并工作可恢复，保留迁移记录和必要归档。

${hash}${hash} 12. 与开发规范的配合

分支规则约束协作与发布，不替代代码质量规范。PR/MR 按改动范围执行[前端](../前端/README.md)、[后端](../后端/README.md)、[数据库](../数据库/README.md)中的检查。版本化迁移已部署后不得因 rebase、squash 或分支清理而改写其内容。

构建与测试权限不等于部署权限。涉及共享环境启动、数据库变更、生产发布和数据清理时，按项目授权与发布流程执行。
